# AI Feature Evaluation Template
Metadata Sovereignty Alliance – AI Capability Review

This template helps evaluate AI tools and features for suitability within ethical, accessible, metadata-aware systems.

Students should complete this template when analysing potential AI technologies.

The goal is to assess:

- usefulness
- transparency
- accessibility
- governance risks
- metadata requirements
- source authority and provenance
- human and participant review boundaries

Accessibility-focused AI is evaluated against the existing EduLinked accessibility authority chain. This template does not create an accessibility standard, learner model, Easy Read model, AAC model, document lifecycle or publication authority.

---

# Feature Overview

## Feature Name
Name of the AI capability.

Example: Plain Language Summarisation

## Description

Brief explanation of what the feature does.

Example: Generates summaries of complex documents to support a more readable representation while preserving traceability to the source.

## Example Tools or Platforms

List existing tools that provide this capability and distinguish product/vendor examples from governed EduLinked authority.

Examples:

- OpenAI summarisation models
- Claude summarisation tools
- open-source transformer summarisation models
- accessibility-focused summarisation systems

---

# Intended Purpose

Explain how this feature could support the organisation’s work.

Examples:

- create a draft alternate representation of complex reports
- assist advocates in reviewing large documents
- support preparation of accessible documentation for community members

Do not describe an output as accessible, Easy Read, AAC-approved, culturally localised or learner-ready merely because the feature can generate it.

---

# Source Artefact and Authority

Identify the source material before proposing a transformation.

Record:

- source-owning system or person
- source artefact identifier/path/URI
- source revision or version
- authorship/provenance state
- consent or permitted-use state
- publication/reuse constraints

The transformed output must remain traceable to the source. A derivative does not replace source truth.

---

# Required Inputs

What information does the AI need?

Examples:

- source text
- document structure
- language model prompt
- metadata fields
- language/localisation context
- attributable accessibility or communication requirement where one exists

Identify sensitive, personal or restricted inputs and whether the proposed use is actually authorised.

---

# Metadata Requirements

What metadata must accompany the record for safe AI processing?

Examples:

- author name or source authority
- creation/revision date
- consent status and permitted purpose
- document purpose
- version number
- source language and target language where translation is proposed
- transformation history
- AI model/tool and version where relevant
- human review status

# Accessibility Requirement and Impact

## Attributable requirement

What accessibility, communication, language, learning or participation requirement is evidenced for this context?

Record the source of that requirement. If no attributable requirement exists yet, record `UNKNOWN` or `NOT_YET_ESTABLISHED`; do not infer a diagnosis, preference or need from the document, tool, cohort label or availability of a format.

## Existing authority to reuse

Inspect and reference the applicable existing EduLinked mechanisms before proposing new semantics:

- Core Easy Read adaptive instructional composition for Easy Read meaning and composition.
- Core accessible-document lifecycle for source preservation, requirements, transformations, checks, human/AT verification, exports and participation-outcome boundaries.
- EduLinked Accessibility System Easy Read entrypoints for the current implementation/navigation projection.
- AccessFlow v1.2.0 for inclusive learning-production requirements, including translation/localisation, signed language, Easy Read, AAC, captions/transcripts, nonvisual access and runtime verification.

`EduLinked-Systems/easy-read` remains production-gated while its source-owned authority-proof issue is open.

## Proposed accessibility effect

Describe the intended effect without converting design intent into outcome evidence.

Examples:

- lower reading demand for a specific purpose
- provide a draft alternate representation
- prepare caption/transcript source material
- support a translated/localised source pathway
- provide a candidate AAC-compatible response pathway

## Production and verification state

Keep these states separate:

- requirement identified
- design included
- source ready
- produced/materialised
- automated checked
- human reviewed
- assistive-technology or specialist verified where applicable
- participant/cohort validated where material
- publication approved

Do not collapse these into one `accessible` flag.

# Transparency Requirements

What information should be visible to users and reviewers?

Examples:

- source document reference
- author/source authority
- AI generation or transformation timestamp
- model/tool and version where relevant
- transformation type
- human review status
- known limitations or semantic-loss warnings
- verification state
- publication authority state

---

# Human Oversight

What human, specialist or participant review should occur?

Examples:

- source owner verifies meaning preservation
- accessibility reviewer evaluates the proposed representation
- AAC/communication specialist reviews AAC or symbol-system decisions where applicable
- competent linguistic/cultural reviewer verifies translation/localisation where stronger claims are made
- participant or representative cohort validates comprehension or usefulness where material
- authorised person approves publication

Human review is not interchangeable with participant comprehension evidence, specialist verification or publication authority.

---

# Risks and Limitations

Potential risks of using this AI feature.

Examples:

- incorrect summaries
- loss of nuance
- semantic flattening during translation or simplification
- misinterpretation of testimony
- inaccessible generated structure
- misleading alt text
- symbol or AAC choices that are not meaningful to intended users
- privacy risks
- provenance loss
- model-generated output being mistaken for source-authoritative content

---

# Ethical Considerations

Questions to consider.

Does the feature:

- preserve authorship and provenance?
- protect sensitive data?
- operate within the permitted purpose and consent scope?
- require explicit consent for the proposed processing?
- preserve source language and meaning where translation is involved?
- avoid harmful profiling or diagnosis inference?
- preserve participant agency and communication preference?
- keep machine inference distinct from person-authored truth?

# Claim Ceilings

Preserve these distinctions:

- `AI_GENERATED != ACCESSIBLE`
- `PLAIN_LANGUAGE != EASY_READ`
- `EMOJI_OR_IMAGE != AAC`
- `TRANSLATED_TEXT != CULTURALLY_LOCALISED`
- `TRANSLATION_VERIFIED != ACCESSIBILITY_VERIFIED`
- `AUTOMATED_CHECK != ACCESSIBILITY_CONFORMANCE`
- `MATERIALISATION != PARTICIPANT_COMPREHENSION`
- `ACCESSIBILITY_OPTION_AVAILABLE != PARTICIPANT_PREFERENCE`
- `ACCESSIBILITY_VERIFICATION != PARTICIPATION_OUTCOME`
- `SUITABLE_FOR_RESEARCH_PILOT != PRODUCTION_OR_PUBLICATION_AUTHORITY`

---

# Recommendation

Final research recommendation.

Possible outcomes:

- Suitable for bounded research or pilot testing
- Suitable with specified safeguards and review gates
- Evidence insufficient; retain as research candidate
- Not recommended

The recommendation must name any unresolved source-authority, accessibility, consent, safeguarding, privacy, learner/participant, publication or external-deployment gate. Template completion does not itself authorise implementation, procurement, publication or participant-facing use.
